# Integrations

All external services sit behind provider interfaces in the API/worker (`NotificationProvider`, `MessagingProvider`, `StorageProvider`, `EmailProvider`, `SmsProvider`, `PaymentProvider`) so vendors can be swapped by configuration and mocked in tests.

## 1. WhatsApp Business (outbound, v1)

Decision: WhatsApp Business Platform (Cloud API via a BSP or directly) from the start; `wa.me` share links are the fallback until approval.

Use cases (all template messages, opt-in required):
1. Daily owner summary (milk, sales, cash, alerts, tasks) at the farm's chosen local time.
2. Invoice and ledger statement to a customer (PDF link or document).
3. Payment receipt and overdue reminders.
4. Staff task and vaccination reminders (opt-in per staff).
5. Invitation links for new users.

Requirements
- Meta Business verification, WhatsApp Business Account, display name approval, phone number dedicated to the platform (not a personal one).
- Templates (utility category) in `en` and `ur`, with named variables; each template has a stored approval status and version. Template changes go through the approval flow before use.
- Consent: per-contact `whatsapp_opt_in` with source and timestamp; opt-out keywords honored; inbound STOP handling updates consent. No marketing messages in v1.
- Delivery: queue job -> provider call -> store `message_log` row (status: queued, sent, delivered, read, failed) from webhooks; retry with backoff on transient errors; never resend the same business event (dedupe key).
- Costs: per-conversation fees tracked in `message_log`; per-farm monthly quota by plan; owner sees usage.
- Webhook endpoint: signature verified, idempotent, rate limited.
- Fallback mode (no approval yet): UI shows "Share on WhatsApp" using `https://wa.me/<phone>?text=<encoded>` with a short secure link to a hosted PDF; no automatic daily summary (push notification + share button instead).
- Phase 2: inbound message parsing for entry with a confirm-before-save step.

Pre-launch tasks (start in Phase 0): choose BSP (compare price, Pakistan number support, template tooling), register business, submit templates, test with a staging number.

## 2. Push notifications

- Expo Push (APNs/FCM) for mobile; Web Push (VAPID) for web PWA/desktop where supported.
- Categories: alerts (by severity), tasks, sync problems, daily summary. Per-user channel settings and quiet hours; critical alerts bypass quiet hours only if the user opts in.
- Device tokens stored per device; invalid tokens pruned on provider feedback.

## 3. Email

- Transactional provider (e.g., Amazon SES, Postmark, Resend): sign-up verification, password reset, invites, statements, platform invoices.
- SPF, DKIM, DMARC configured; bounce/complaint webhooks suppress addresses; templates localized en/ur with plain-text alternative.

## 4. SMS / OTP

- Provider with Pakistan coverage (local aggregator or international such as Twilio) behind `SmsProvider`; used for phone verification, OTP login, and fallback invites.
- Per-number and per-IP throttles; cost guard per farm and global daily cap; alerts on spikes (SMS pumping fraud).

## 5. Object storage

- S3-compatible (AWS S3, Cloudflare R2, RustFS in local dev, see ADR-019). Private buckets; keys `farm/<farm_id>/<entity>/<uuid>.<ext>`; signed URLs (<= 10 min) for upload and download.
- Image pipeline in worker: validate, strip EXIF, resize variants (thumb 256, medium 1024), WebP/AVIF for web; AV scan before marking `ready`.
- Lifecycle: abandoned uploads deleted after 24 h; exports expire after 7 days.

## 6. Reports and documents

- PDF generation (invoices, statements, passports, QR label sheets, payslips) in worker using a headless renderer or `@react-pdf/renderer`, with Urdu shaping fonts embedded and RTL tested.
- CSV/XLSX exports streamed; large exports as background jobs delivered via signed URL notification.

## 7. Payments (Phase 2)

- Subscription collection: JazzCash / Easypaisa / bank-transfer verification for Pakistan; Stripe for international. Behind `PaymentProvider`; webhook-driven subscription state; invoices generated by platform. In v1, super admin marks platform invoices as paid.

## 8. Maps and location

- Attendance geofence uses device coordinates with a simple radius check on the farm location (no third-party maps API needed in v1). Map tiles only for the farm-location picker (OpenStreetMap-based, self-proxied or a commercial provider).

## 9. Device and hardware (QR/NFC)

- QR: camera scanning (expo-camera / barcode scanner); label format `https://<app-domain>/a/<short_id>` resolves to the animal for logged-in users and to the public passport if published.
- NFC: read NDEF tags (iOS and Android where hardware allows); fallback to QR when NFC is unavailable. Tag write supported on Android.
- Phase 3: Bluetooth scales and milk meters via vendor SDKs behind a `DeviceAdapter` interface.

## 10. Observability

- Sentry (web, mobile, API, worker), OpenTelemetry traces to a collector (Grafana Tempo or vendor), metrics via Prometheus/Grafana, uptime monitoring and status page.

## 11. Integration failure handling

- Every outbound call has timeouts, retries with jitter, circuit breaker, and a dead-letter queue visible in the admin console.
- User-visible degradation is explicit (e.g., "WhatsApp is unavailable; we'll retry. You can also share manually").
- Provider credentials are stored encrypted, rotated via runbook, and never logged.
